causality, a distributed trace analysis tool

oct, 2026

Understanding a performance regression is not just about finding a slow operation. In a distributed system, an operation's latency can reflect work performed by its descendants, making it difficult to distinguish where a slowdown appears from where further investigation should begin.

Causality is a distributed trace analysis tool that compares baseline and degraded trace datasets, identifies operation-level latency regressions, and organizes supporting evidence to help developers investigate potential performance bottlenecks.

The goal is to turn raw trace data into a structured comparison without treating every observed latency increase as proof of a root cause.

the problem with latency regression analysis

Distributed traces represent application execution through spans. Each span records an operation, its service, its timing, and potentially its relationship to a parent span. Together, these relationships provide a view of execution across services.

When performance degrades, raw traces can contain many operations with increased latency. Some increases may represent independent regressions, while others may reflect time spent waiting for slower descendant operations.

Comparing individual spans without accounting for operation aggregation, sample counts, and execution relationships can make investigation noisy. Developers need a repeatable way to compare datasets and prioritize the evidence that deserves attention.

turning traces into comparable evidence

Causality validates incoming trace data, normalizes spans into a canonical representation, and groups observations by service and operation. It summarizes operation durations using medians and compares matched operations across baseline and degraded datasets.

Regression candidates are ranked using latency deltas and supporting sample counts. This provides a consistent view of which operations changed and by how much, rather than relying on isolated span durations.

The analysis pipeline is separated from the web layer so that trace validation, operation summarization, regression ranking, and evidence reporting can be tested independently of request handling and presentation.

reasoning about execution relationships

A parent operation can appear slower because work further down its execution tree has become slower. Causality therefore incorporates descendant regression evidence into a second ranking approach.

This execution-aware analysis helps distinguish operations with their own observed latency increases from potential parent symptoms associated with slower descendants. It adds context to the ranking instead of treating every increase as an independent bottleneck.

These classifications are investigation heuristics, not proof of causality. The evidence helps narrow the search, while confirming a root cause still requires further analysis.

building a reliable trace ingestion workflow

The application supports trace datasets supplied as pasted JSON or uploaded JSON files, along with an integration for ingesting traces through the Jaeger Query API.

Incoming data is validated before analysis. Structural checks cover span identifiers, parent references, timestamps, and execution relationships. Request and dataset size limits help keep malformed or oversized inputs within defined boundaries.

A normalized trace representation keeps the analysis pipeline independent of the original ingestion path. This creates a consistent boundary between external trace data and the application's internal analysis model.

making comparisons persistent and inspectable

Successful comparison runs are stored through Django's ORM. Persisted information includes normalized input datasets, trace counts, matched operation counts, regression candidate counts, ranked results, and supporting evidence.

PostgreSQL support enables deployment with a hosted relational database, while SQLite remains available for local development. Database migrations provide a repeatable way to manage the application's schema.

Persistence establishes a record of successful analyses. A dedicated user-facing history interface and per-user access separation are not currently implemented.

testing the analysis, not just the interface

Causality emphasizes deterministic analysis and explicit validation rules. Automated tests cover trace parsing, operation matching, latency ranking, execution-aware evidence, invalid inputs, request limits, ingestion workflows, and database persistence.

The project has reached 114 passing automated tests, alongside Django system checks and deployment-oriented validation. These checks provide evidence that the implemented behaviors work under the tested conditions, rather than a guarantee against every production failure.

what i'm optimizing for

The goal is to make distributed performance investigation more structured, explainable, and repeatable. That requires more than calculating latency differences: it requires validating the data, preserving execution relationships, exposing the evidence behind rankings, and communicating the limits of each conclusion.

Causality is built with Python, Django, PostgreSQL support, automated tests, and a modular trace-analysis pipeline. The application is deployed on Render. Hosted Jaeger ingestion still requires a reachable Jaeger endpoint to be configured; a local endpoint on a developer's machine is not accessible to the hosted service by default.

The implementation and its tests determine what the project currently supports. Regression classifications prioritize investigation; they do not establish definitive causal relationships between distributed operations.
